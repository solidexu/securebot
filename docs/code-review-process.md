## 📋 流程概览

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│  Step 1: APP哥 开发代码 (GLM-5)                            │
│          ─────────────────────────────                     │
│          快速迭代，写功能代码                               │
│                                                             │
│  Step 2: APP哥 发消息「代码写好了，请审查」                │
│          ─────────────────────────────                     │
│          在飞书群中发消息                                   │
│                                                             │
│  Step 3: APP哥 通知老大                                    │
│          ─────────────────────────────                     │
│          sessions_send 消息到主会话                        │
│                                                             │
│  Step 4: 老大 spawn Qwen-Coder 审查 agent                  │

│  Step 5: 审查 agent 返回报告                               │
│          ─────────────────────────────                     │

```

## 🎯 角色分工

| 角色 | 模型 | 职责 |
|------|------|------|
| **APP哥** | GLM-5 | 开发代码、修复问题 |
| **老大** | GLM-5 | spawn 审查 agent |
| **审查 agent** | Qwen-Coder | 独立代码审查 |
| **主人** | - | 最终测试、合并决策 |

---

## 🔧 技术实现

### Step 1-2: 开发完成

APP哥 在飞书群发消息：
```
代码写好了，请审查
```

### Step 3: 通知老大

```typescript
// APP哥 调用
sessions_send({
  sessionKey: 'agent:main:main',
  message: '@所有人 APP哥代码已准备好，请启动代码审查。'
});
```

### Step 4: 启动审查

```typescript
// 老大 调用
sessions_spawn({
  mode: 'run',
  model: 'qwen/qwen-coder',
  task: '审查 SecureBot dev 分支代码...',
  timeoutSeconds: 300
});
```

### Step 5: 审查报告

审查 agent 返回结构化报告：

```markdown
## 审查报告

### 🔴 严重问题 (必须修复)
- [问题列表]

### 🟡 中等问题 (建议修复)
- [问题列表]

### 🟢 小问题 (可选优化)
- [问题列表]

### ✅ 亮点
- [做得好的地方]
```

---

## 📊 审查标准

### 严重问题 (P0) - 必须修复

| 类型 | 说明 |
|------|------|
| 安全漏洞 | 命令注入、XSS、敏感信息泄露 |
| 运行时错误 | 类型错误、空指针、未处理异常 |
| 架构问题 | 循环依赖、模块耦合过高 |
| 无测试覆盖 | 核心功能无测试 |

### 中等问题 (P1) - 建议修复

| 类型 | 说明 |
|------|------|
| 性能问题 | 内存泄漏、N+1 查询 |
| 代码质量 | 重复代码、过长函数 |
| 类型安全 | any 类型、类型断言过多 |
| 错误处理 | 异常处理不完整 |

### 小问题 (P2) - 可选优化

| 类型 | 说明 |
|------|------|
| 代码风格 | 命名不规范、注释缺失 |
| 可维护性 | 魔法数字、硬编码 |
| 文档 | 缺少注释、文档不一致 |

## 🚀 分支策略

```
main  ← 稳定版本（只有经过测试的功能才能合并）
dev   ← 开发分支（新功能先在这里）
```

### 合并条件

```
✅ 审查通过（无 P0 问题）
✅ 主人测试通过
✅ 类型检查通过
✅ Lint 检查通过
```

### 合并命令

```bash
git checkout main
git merge dev
git push origin main
git push github main
```

## 📝 检查清单

### 开发阶段

- [ ] 功能实现完成
- [ ] 类型检查通过 (`npm run typecheck`)
- [ ] Lint 检查通过 (`npm run lint`)
- [ ] 单元测试通过 (`npm test`)

### 审查阶段

- [ ] 通知老大启动审查
- [ ] 收到审查报告
- [ ] 修复所有 P0 问题
- [ ] 考虑修复 P1 问题

### 测试阶段

- [ ] 主人在真实环境测试
- [ ] 验证核心功能
- [ ] 验证边界情况

### 合并阶段

- [ ] 主人确认合并
- [ ] 合并到 main
- [ ] 推送到远程仓库

---

## 🔒 安全原则

1. **审查者分离**：开发模型和审查模型必须不同
2. **人工验收**：最终决策由主人做出
3. **分支保护**：main 分支只接受测试通过的代码
4. **代码签名**：建议启用 GPG 签名
